1. Vue d’ensemble
MyJobPilot est une application Django de suivi de recherche d’alternance et d’accompagnement d’élèves. Elle couvre les prospections et candidatures, les entreprises, les relances, les documents, les objectifs, les tableaux de bord, les notifications et la gamification.

Ses publics sont les élèves, les superviseurs qui suivent les élèves de leur périmètre et les administrateurs.

4. Rôles et permissions
Rôle	Accès général
eleve	Gère ses propres démarches et consulte ses données personnelles
superviseur	Suit les élèves couverts par ses scopes actifs
admin	Gère les données métier à travers les vues d’administration


Le rôle métier admin est distinct de is_staff et is_superuser. L’accès à /admin/ dépend des permissions Django.
Scope superviseur
ScopeSuperviseur(superviseur, centre, is_active) associe un superviseur à un centre. Les élèves accessibles sont ceux du rôle élève rattachés à un centre dans un scope actif.

Pattern utilitaire : centres_du_superviseur(user), superviser_eleve(user, eleve) et verifier_superviseur(request, eleve=None). Ce dernier lève PermissionDenied hors scope, transformé par Django en réponse 403. Les vues qui manipulent un élève appliquent également un queryset limité au périmètre.

5. Flux utilisateurs principaux
5.1 Inscription, validation, première connexion
1. Inscription via /comptes/inscription/.
2. comptes.views.inscription valide le formulaire et journalise l’événement.
3. Le compte est créé avec is_valide=False.
4. L’admin valide ou refuse le compte.
5. Connexion via /comptes/connexion/, puis redirection selon rôle et validation : admin, superviseur, élève en attente ou élève validé vers /dashboard/.
Modèles : Utilisateur, JournalAction, éventuellement Notification, ConsentementRGPD.
5.2 Créer une prospection
1. Depuis /dashboard/, l’élève ouvre /entreprises/nouvelle/.
2. La vue vérifie le rôle, l’entreprise et les doublons.
3. Elle crée Prospection et HistoriqueStatut.
4. La redirection revient au détail ou au dashboard selon le parcours.
5.3 Modifier un statut
1. Détail /entreprises/<id>/.
2. POST vers la route de changement de statut.
3. Contrôle propriétaire/scope, validation, mise à jour de la prospection et date métier éventuelle.
4. Création de HistoriqueStatut, journalisation et notification si la modification est faite par le superviseur/admin pour un élève.
5.4 Effectuer une relance
1. Depuis /mes-relances/, POST vers /mes-relances/creer/.
2. mes_relance_creer vérifie propriétaire, scope superviseur ou rôle admin.
3. Crée Relance, met à jour l’échéance Prospection.date_relance, et peut faire passer a_relancer à en_attente.
4. L’élève reçoit une notification si la relance est effectuée par quelqu’un d’autre.
5. Les badges sont recalculés puis la vue redirige vers /mes-relances/.
5.5 Badges et progression
L’élève ouvre /mon-compte/badges/. La vue vérifie les badges et notifications de progression, assemble XP, niveau, points et progression par catégorie, puis affiche les ancres #badge-<slug>.
5.6 Superviseur
Depuis /staff/, le superviseur consulte les élèves de ses scopes, puis /staff/eleves/<id>/. La fiche revalide le scope et présente les données autorisées, dont les prospections, badges et progression.
5.7 Admin
Depuis /admin-dashboard/, l’administrateur consulte les listes, filtres, imports/exports, KPI, scopes et fiches élèves. L’admin Django permet la gestion de modèles configurables si le compte dispose de is_staff.
6. Gamification — lots 22a à 22d
Modèles et règles
- Relance représente une action réellement effectuée ; Prospection.date_relance reste une échéance.
- Badge est configurable par l’admin ; le slug est stable après création.
- BadgeObtenu persiste l’attribution, unique par couple utilisateur/badge.
- Niveau est configurable en base ; les migrations initialisent sept niveaux.
Les 17 badges initiaux, tous à 10 points :
Catégorie	Seuils et slugs	Noms initiaux
Prospection	prospection-10, -20, -35, -50, -75, -100	Novice, Explorateur, Persévérant, Chasseur, Stratège, Expert
Candidature	candidature-3, -5, -10, -15, -25	Premier pas, Candidat motivé, Candidat engagé, Candidat déterminé, Candidat confirmé
Suivi	relance-1, -3, -5, -10, -15, -25	Premier suivi, Relanceur, Insistant, Persévérant, Accrocheur, Roi de la relance


Les sept seuils de niveau sont : Novice 0, Explorateur 100, Persévérant 250, Chasseur 500, Stratège 1 000, Expert 2 000, Ambassadeur 4 000.
Compteurs et calculs
- Prospections contactées : toutes sauf les statuts a_contacter et terminee.
- Candidatures : candidature_envoyee, en_attente, entretien_programme, refus, accepte.
- Relances : objets Relance liés aux prospections de l’élève.
- XP calculés à la demande : 10 par prospection contactée, 20 par candidature, 10 par relance.
- Points : somme des points des badges obtenus ; ce n’est pas un solde XP.
- Progression vers le prochain badge : compteur actuel divisé par seuil cible, plafonné à 1.

7. Notifications — lot 21a et extensions
Notification est définie dans comptes. Les types existants sont compte_valide, compte_refuse, statut_change, relance_creee, codes_rome_modifies, commentaire, document, ajout_prospection, badge_obtenu, progression_badge.

ajout_prospection est un type historique ; la création d’une prospection ne notifie plus.

creer_notification(destinataire, type, message, lien="") crée une notification si l’utilisateur destinataire existe et est actif. Les notifications métier sont créées par appels explicites, pas par un système général de signaux.

Routes principales :
- /notifications/ : liste personnelle paginée.
- /notifications/unread-count/ : compteur JSON.
- /notifications/<pk>/lue/ : POST de marquage en lecture.
- /notifications/tout-lu/ : POST de marquage global.
La cloche et son compteur sont dans templates/base.html; le compteur initial est fourni par un context processor et le polling se fait toutes les 60 secondes. La vue vérifie l’appartenance et la sûreté du lien avant redirection.

15. Glossaire
Terme	Définition
Prospection	Démarche d’un élève auprès d’une entreprise, suivie par statut, dates et historique.
Entreprise	Fiche de référentiel partagée, associable à plusieurs élèves.
Candidature	Étape représentée actuellement par des statuts de Prospection ; pas de modèle autonome.
Relance	Événement historisé réellement effectué ; distinct de l’échéance date_relance.
Badge	Récompense configurable basée sur un seuil prospection, candidature ou relance.
Badge obtenu	Attribution persistante unique par utilisateur et badge.
Niveau	Palier configurable et calculé à partir des XP.
XP	Expérience recalculée à la demande depuis l’activité.
Points	Somme des valeurs des badges obtenus.
Scope superviseur	Liaison active entre superviseur et centre donnant accès aux élèves de ce centre.
Centre	Regroupement des élèves et formations.
Formation	Parcours rattaché à un centre.
ROME	Code métier stocké sur le profil et transmis à LBA ; aucun mot-clé n’est converti automatiquement.
LBA	La bonne alternance, source externe d’offres et de recruteurs.
KPI	Indicateur agrégé des dashboards.
Historique de statut	Enregistrement d’une transition de statut, son auteur et sa date associée éventuelle.
Notification in-app	Message stocké en base, affiché dans la cloche et la page notifications.
Demande RGPD	Demande d’exercice d’un droit enregistrée puis traitée.

20.5 Rollback
Revert propre d’un commit
git fetch origin main
git checkout main
git pull origin main
git revert <hash-du-commit-casse> --no-edit
git push origin main

Le workflow redéploie le revert.

Revert de plusieurs commits depuis un tag connu

Pour produire un seul commit de rollback :
git fetch origin main
git checkout main
git pull origin main
git revert --no-commit v0.23.8-lot23f..HEAD
git commit -m "Rollback après v0.23.8-lot23f"
git push origin main

Vérifier d’abord que le tag représente bien l’état à restaurer et que les migrations sont compatibles. Un revert de code ne restaure pas automatiquement les données supprimées ou transformées par une migration.

Urgence VPS

Un checkout temporaire sur tag peut dépanner une instance, mais place le dépôt en detached HEAD :
sudo -u myjobpilot bash -lc 'cd /home/myjobpilot/MyJobPilot && git checkout v0.23.8-lot23f'
sudo systemctl restart myjobpilot

C’est un dépannage temporaire. Il faut ensuite rétablir un état suivi par main et publier un revert Git propre ; sinon, le déploiement suivant peut remettre le code problématique.

À ne jamais faire : git reset --hard suivi d’un force push pour réécrire main.
20.6 Pièges à éviter
Cache CSS du service worker
- custom.css et tokens.css sont en network-first.
- En cas de rendu ancien, faire un hard refresh ; si nécessaire, ouvrir DevTools → Application → Service Workers → Unregister puis recharger.
Commit local absent de GitHub

Après chaque publication via la connexion GitHub, faire :
git fetch origin main
git reset --hard origin/main
git log --oneline -3
git status

Ne pas construire le lot suivant sur un commit local absent de origin/main.

Force push

Ne pas utiliser git push --force. Il réécrit l’historique et peut désynchroniser les clones.

Troncature GitHub

Après création d’un commit via GitHub, contrôler que les fichiers et le tree correspondent au résultat testé localement. Si une troncature est constatée, publier un commit correctif et le signaler ; les tests doivent rester verts.
20.7 En cas de doute
git status
git log --oneline -5
git fetch origin main

Vérifier ensuite Actions, le SHA réellement déployé sur le VPS et l’erreur constatée. Ne pas lancer de reset avant d’avoir identifié les modifications locales qui seraient perdues. Ne pas oublier de vérifier le workflow après publication et de taguer la version validée.
